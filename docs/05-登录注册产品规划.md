# ResearchOS 登录注册产品规划 v1.0

> 自建认证系统 + 多租户注册 — 完整产品功能设计

---

## 一、功能定位

**核心目标**：为 ResearchOS 提供独立的用户认证与租户管理能力，支持邮箱密码注册、JWT 鉴权、多租户隔离和团队成员管理。

**设计原则**：
1. **自建认证**：不依赖第三方 Auth SDK，完整管控用户凭证生命周期
2. **租户优先**：注册即创建组织，团队协作为核心使用模式
3. **安全基线**：密码加密存储、JWT + Refresh Token、CSRF 防护、暴力破解防护
4. **渐进扩展**：预留 OAuth 第三方登录扩展点，但 MVP 仅实现邮箱密码

## 三、页面设计

### 3.1 页面清单

| 页面 | 路由 | 说明 | 是否需登录 |
|------|------|------|-----------|
| 登录页 | `/login` | 邮箱+密码登录 | 否 |
| 注册页 | `/register` | 新用户注册（邮箱+密码+用户名） | 否 |
| 邮箱验证页 | `/verify-email` | 输入/自动验证邮箱验证码 | 否 |

| 重置密码页 | `/reset-password/:token` | 设置新密码 | 否 |
| 个人设置页 | `/settings/profile` | 修改个人信息和密码 | 是 |
| 团队管理页 | `/settings/team` | 管理成员、邀请、角色（admin 可见） | 是 |

## 四、详细功能设计

### 4.1 注册流程（流程 A）

#### Step 1: 填写注册信息

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|---------|
| 用户名 | text | ✅ | 2-50 字符 |
| 邮箱 | email | ✅ | 合法邮箱格式，全局唯一 |
| 密码 | password | ✅ | 至少 8 位，包含大小写字母和数字 |
| 确认密码 | password | ✅ | 与密码一致 |
| 服务条款 | checkbox | ✅ | 必须勾选 |

**前端校验**：
- 邮箱格式实时校验
- 密码强度实时提示（弱/中/强）
- 密码与确认密码一致性校验
- 提交前所有字段非空校验

**后端校验**：
- 邮箱唯一性校验（含已注册未验证的）
- 密码复杂度二次校验
- 同一 IP 注册频率限制：10 次/小时

#### Step 2: 邮箱验证

| 项目 | 说明 |
|------|------|
| 验证方式 | 6 位数字验证码 |
| 有效期 | 10 分钟 |
| 重发间隔 | 60 秒 |
| 最大重发次数 | 5 次/小时 |
| 最大尝试次数 | 5 次（超过后需重新获取验证码） |
| 验证码存储 | Redis，key: `verify:{email}`，TTL: 600s |

**时序图**：
```
用户        前端          后端            邮件服务         Redis
 │          │             │               │               │
 │─注册────▶│─POST /auth/register─────▶│               │
 │          │             │─生成验证码──────────────────▶│ SET verify:{email}
 │          │             │─发送验证邮件───▶│               │
 │          │◀─ 200 OK ──│               │               │
 │◀─跳转───│             │               │               │
 │  验证页  │             │               │               │
 │          │             │               │               │
 │─输入码──▶│─POST /auth/verify-email─▶│               │
 │          │             │─校验验证码──────────────────▶│ GET verify:{email}
 │          │             │─标记邮箱已验证  │               │ DEL verify:{email}
 │          │◀─ 200 + tempToken ────── │               │
 │◀─跳转───│             │               │               │
 │  创建组织│             │               │               │
```

#### Step 3: 创建组织

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|---------|
| 组织名称 | text | ✅ | 2-100 字符 |
| 所属行业 | select | ❌ | 预设行业列表 |
| 团队规模 | select | ❌ | 1-10 / 11-50 / 51-200 / 200+ |
| 邀请邮箱列表 | text[] | ❌ | 最多 10 个，合法邮箱格式 |

**行业列表**：
```
互联网/科技 | 金融/保险 | 消费品/零售 | 医疗/健康 | 教育/培训 |
制造/工业 | 房地产 | 咨询/专业服务 | 媒体/传播 | 政府/公共事业 | 其他
```

**创建组织后**：
1. 创建 Tenant 记录，plan 默认 `free`
2. 将当前用户 role 设为 `admin`，关联到新 Tenant
3. 如有邀请邮箱，自动创建邀请记录并发送邀请邮件
4. 签发正式 JWT Token（含 tenantId + role）
5. 跳转到仪表盘（首次可显示新手引导）

### 4.2 邀请加入流程（流程 B）

#### 邀请创建（管理员操作）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 被邀请人邮箱 | email | ✅ | 不能是已在本租户内的成员 |
| 分配角色 | select | ✅ | `analyst`（默认） / `viewer` |

**邀请约束**：
- 单个租户最多 50 个未接受的邀请
- 同一邮箱对同一租户只能有 1 个有效邀请
- 邀请有效期：7 天
- 邀请链接格式：`{BASE_URL}/invite/{inviteToken}`

#### 受邀注册

1. 用户点击邮件中的邀请链接
2. 系统校验 inviteToken 有效性（未过期、未使用、未取消）
3. 展示邀请信息（组织名称、邀请人）
4. 用户填写姓名和密码
5. 创建用户，自动关联到邀请者的 Tenant，角色为邀请时指定的角色
6. 标记邀请为已使用
7. 签发 JWT Token，跳转到仪表盘

**特殊情况**：
- 如果邮箱已在其他租户注册 → 提示 "该邮箱已有账号，请登录后在设置中加入新组织"（MVP 暂不支持多租户）
- 如果邀请已过期 → 展示过期提示 + 联系管理员按钮
- 如果邀请已取消 → 展示已取消提示

### 4.3 登录流程（流程 C）

#### 登录表单

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 邮箱 | email | ✅ | 已注册且已验证的邮箱 |
| 密码 | password | ✅ | 正确的密码 |
| 记住我 | checkbox | ❌ | 勾选后 Refresh Token 有效期延长到 30 天 |

#### 暴力破解防护

| 策略 | 阈值 | 动作 |
|------|------|------|
| 同一账号连续失败 | 5 次 | 锁定账号 15 分钟 |
| 同一账号连续失败 | 10 次 | 锁定账号 1 小时 |
| 同一 IP 登录失败 | 20 次/小时 | 要求图形验证码 |
| 同一 IP 登录失败 | 50 次/小时 | 封禁 IP 1 小时 |

#### Token 策略

| Token | 有效期 | 存储位置 | 说明 |
|-------|--------|---------|------|
| Access Token (JWT) | 15 分钟 | 内存 (前端状态) | 携带 userId, tenantId, role |
| Refresh Token | 7 天（记住我: 30 天） | HttpOnly Cookie | 用于无感刷新 Access Token |
| 临时 Token | 30 分钟 | 内存 | 邮箱验证后、创建组织前的过渡 Token |

## 七、安全设计

### 7.1 密码安全

| 项目 | 策略 |
|------|------|
| 加密算法 | bcrypt（cost factor = 12） |
| 密码规则 | 最少 8 位，包含大写字母、小写字母、数字 |
| 密码历史 | 不能与最近 3 次密码相同 |
| 传输安全 | 全站 HTTPS，密码明文传输（TLS 加密信道） |

### 7.2 Token 安全

| 项目 | 策略 |
|------|------|
| JWT 签名 | HS256（开发）/ RS256（生产） |
| JWT Secret | 环境变量，定期轮换 |
| Refresh Token | 存储 SHA-256 Hash，非原文 |
| Refresh Token 轮换 | 每次刷新签发新 RT，旧 RT 立即失效 |
| Cookie 属性 | HttpOnly, Secure, SameSite=Strict |

### 7.3 防护措施

| 威胁 | 防护 |
|------|------|
| 暴力破解 | 账号锁定 + IP 限流 + 图形验证码 |
| CSRF | SameSite Cookie + CSRF Token（表单提交场景） |
| XSS | HttpOnly Cookie（RT 不可被 JS 读取） |
| 邮箱枚举 | 忘记密码不透露邮箱是否存在 |
| Token 泄露 | 短有效期 AT + RT 轮换 + 设备绑定 |
| 邀请链接攻击 | 一次性使用 + 7 天过期 + UUID v4 令牌 |

### 7.4 审计日志

以下操作自动记录到 AuditLog：

| 操作 | action 值 | 说明 |
|------|----------|------|
| 注册 | `user_register` | 新用户注册 |
| 登录 | `user_login` | 登录成功 |
| 登录失败 | `user_login_failed` | 登录失败（含失败原因） |
| 登出 | `user_logout` | 用户登出 |
| 密码修改 | `password_change` | 用户修改密码 |
| 密码重置 | `password_reset` | 通过重置链接修改密码 |
| 角色变更 | `role_change` | 管理员修改成员角色 |
| 成员邀请 | `member_invite` | 管理员发送邀请 |
