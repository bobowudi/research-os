### 关键设计原则

1. **无公网实时搜索**：系统不提供实时公网搜索功能，外部数据通过 M10 数据源管理模块定期爬取并存入证据库
2. **证据来源二分法**：`sourceCategory` 仅有 `internal`（内部）和 `external`（外部）两类
3. **洞察中间层**：M4 洞察管理作为证据与决策之间的中间层，AI 在推理过程中自动生成洞察，用户也可手动创建
4. **对抗推理数据源分离**：正方 Agent 使用内部证据，反方 Agent 使用外部证据（均来自证据库，非实时搜索）

| 手动修正 | 用户手动修改立场判断结果 | P0 |

#### 证据自动关联机制

当新证据入库时（手动创建、批量导入、M10 爬虫采集），系统自动检查是否与现有 active 议题相关并推荐关联：

```
新证据入库
    │
    ▼
Step 1: Embedding 生成
    │  对证据内容生成向量 embedding
    ▼
Step 2: 议题匹配
    │  与所有 status ∈ ['collecting', 'analyzing'] 的议题做语义相似度匹配
    ▼
Step 3: 阈值判断
    │  relevanceScore ≥ 0.7 → 自动关联（relationType='auto'）
    │  0.5 ≤ relevanceScore < 0.7 → 推荐关联（通知用户确认）
    │  relevanceScore < 0.5 → 不关联
    ▼
Step 4: 自动立场分析
    │  对自动关联的证据自动触发 stance 分析
    ▼
Step 5: 通知
    └── 通知议题 owner："有 N 条新证据自动关联到您的议题"
```

```typescript
interface AutoAssociationConfig {
  enabled: boolean                   // 是否启用自动关联，默认 true
  autoLinkThreshold: number          // 自动关联阈值，默认 0.7
  suggestThreshold: number           // 推荐关联阈值，默认 0.5
  maxIssuesPerEvidence: number       // 单条证据最多自动关联的议题数，默认 5
  autoAnalyzeStance: boolean         // 自动关联时是否自动分析立场，默认 true
  targetIssueStatuses: string[]      // 参与匹配的议题状态，默认 ['collecting', 'analyzing']
}
```

对应 API：
```

GET    /api/evidence/:id/suggested-issues               # 获取推荐关联的议题列表
POST   /api/evidence/batch-auto-associate               # 批量自动关联（如 ImportJob 完成后调用）
```

### M4: 洞察管理 (Insight) ⭐ 新增模块

**核心职责**：作为证据与决策之间的中间层，将离散的证据和立场分析结果凝练为结构化洞察。AI 在推理过程中自动生成洞察，用户也可手动创建、确认或争议洞察。每条洞察链接到支撑它的证据。

#### 功能点

| 功能 | 描述 | 优先级 |
|------|------|--------|
| AI 自动生成洞察 | 对抗推理过程中 AI 自动提炼洞察 | P0 |
| 手动创建洞察 | 用户基于经验手动创建洞察 | P0 |
| 确认/争议 | 用户对洞察标记确认（confirmed）或争议（disputed） | P0 |
| 证据链接 | 每条洞察关联支撑它的证据列表 | P0 |
| 洞察分类 | 按类型分类：发现、风险、机会、矛盾 | P1 |
| 洞察评分 | 基于支撑证据的数量和质量自动评分 | P1 |
| 洞察合并 | 合并相似或重复的洞察 | P2 |
| 洞察导出 | 导出洞察摘要报告 | P2 |

#### 数据模型

### M5: 对抗推理引擎 (Reasoning Engine)

**核心职责**：运行内外对抗推理，正方 Agent 使用内部证据构建支持论据，反方 Agent 使用外部证据构建反驳论据，裁判 Agent 综合双方生成决策卡。推理过程中自动生成洞察（M4）。

> **关键设计**：反方 Agent 使用的外部证据来自证据库（通过 M10 定期爬取入库），**不进行实时公网搜索**。

#### 功能点

| 功能 | 描述 | 优先级 |
|------|------|--------|
| 正方推理 | 基于内部证据（`sourceCategory='internal'`）构建支持论据 | P0 |
| 反方推理 | 基于外部证据（`sourceCategory='external'`）构建反驳论据 | P0 |
| 裁判推理 | 综合正反方输出生成决策卡 | P0 |
| 自动生成洞察 | 推理过程中自动提炼洞察写入 M4 | P0 |
| 流式输出 | 推理过程实时流式展示 | P1 |
| 推理过程可视化 | 展示推理链路、证据引用关系 | P1 |
| 中断恢复 | 支持中断后继续推理 | P2 |
| 版本管理 | 同一议题多次推理版本对比 | P2 |

#### Agent 数据源配置

```typescript
/**
 * Agent 数据源规则
 * - 正方 Agent: 仅使用内部证据
 * - 反方 Agent: 仅使用外部证据（来自证据库，非实时搜索）
 * - 裁判 Agent: 综合使用全部证据 + 正反方输出
 */
interface AgentDataSource {
  advocate: {
    internalEvidence: true       // ✅ 内部证据（sourceCategory='internal'）
    externalEvidence: false      // ❌ 不使用外部证据
    realtimeSearch: false        // ❌ 无实时搜索
  }
  critic: {
    internalEvidence: false      // ❌ 不直接使用（仅参考以发现漏洞）
    externalEvidence: true       // ✅ 外部证据（sourceCategory='external'，来自证据库）
    realtimeSearch: false        // ❌ 无实时搜索
  }
  judge: {
    advocateOutput: true         // ✅ 正方输出
    criticOutput: true           // ✅ 反方输出
    allEvidence: true            // ✅ 全部证据
    insights: true               // ✅ 已有洞察
  }
}
```

#### 推理边界处理策略

当内外证据数量不平衡时，系统采取以下降级策略：

| 场景 | 内部证据数 | 外部证据数 | 处理策略 |
|------|-----------|-----------|----------|
| 正常 | ≥ 3 | ≥ 3 | 标准对抗推理流程 |
| 外部不足 | ≥ 3 | 1-2 | 反方 Agent 额外获取 neutral 立场的内部证据作为参考视角，输出标注"外部证据有限" |
| 内部不足 | 1-2 | ≥ 3 | 正方 Agent 额外获取 neutral 立场的外部证据作为参考视角，输出标注"内部证据有限" |
| 单方缺失 | 0 | ≥ 1 | 仅执行反方分析，裁判标注"单方推理 — 缺少内部视角"，决策卡置信度自动降低 20% |
| 单方缺失 | ≥ 1 | 0 | 仅执行正方分析，裁判标注"单方推理 — 缺少外部视角"，决策卡置信度自动降低 20% |
| 双方缺失 | 0 | 0 | 拒绝推理，返回错误提示"请先关联证据" |
| 严重不平衡 | ≥ 10 | 1-2 (或反之) | 正常推理，但裁判输出中增加"证据不平衡警告"，建议补充弱势方证据 |

```typescript
interface ReasoningPreflightCheck {
  canProceed: boolean
  mode: 'standard' | 'degraded_external' | 'degraded_internal' | 'single_side' | 'refused'
  warnings: string[]
  internalEvidenceCount: number
  externalEvidenceCount: number
  suggestion?: string              // 如 "建议补充至少 3 条外部证据后再推理"
}
```

推理触发前，系统自动执行 preflight check 并返回给前端展示：
```
POST /api/issues/:id/reasoning/preflight      # 推理前置检查（不实际触发推理）
```

#### 推理流程

```
┌────────────────────────────────────────────────────────────────────────┐
│                         对抗推理流程                                    │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  Step 1: 数据准备                                                      │
│  ├── 获取议题关联的内部证据 (sourceCategory='internal', stance='pro')  │
│  ├── 获取议题关联的外部证据 (sourceCategory='external', stance='con') │
│  └── 加载议题现有洞察 (M4)                                            │
│                                                                        │
│  Step 2: 正方推理 (Advocate Agent) ──┐                                │
│  ├── 输入: 内部证据 + 议题信息        │                                │
│  ├── 处理: 构建支持论据              │── 并行执行                      │
│  ├── 输出: AdvocateOutput            │                                │
│  └── 副作用: 生成 finding 类洞察     │                                │
│                                       │                                │
│  Step 3: 反方推理 (Critic Agent) ────┘                                │
│  ├── 输入: 外部证据 + 正方盲点提示                                    │
│  ├── 处理: 构建反驳论据 + 识别风险                                    │
│  ├── 输出: CriticOutput                                               │
│  └── 副作用: 生成 risk/contradiction 类洞察                           │
│                                                                        │
│  Step 4: 裁判推理 (Judge Agent) ── 串行                               │
│  ├── 输入: 正方输出 + 反方输出 + 全部证据 + 全部洞察                  │
│  ├── 处理: 综合评估、调解冲突、生成推荐                               │
│  ├── 输出: JudgeOutput { recommendation, confidence, actions }        │
│  └── 副作用: 生成 opportunity 类洞察                                  │
│                                                                        │
│  Step 5: 决策卡生成                                                    │
│  └── 基于裁判输出生成结构化 DecisionCard (M6)                         │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

```
信号检测触发时机：

1. 新证据入库触发（增量）
   ├── DataSource 同步完成（ImportJob status → completed）
   ├── 手动导入证据
   └── 触发对新入库证据的增量信号扫描

2. 定时全量扫描（批量）
   ├── Cron Job: 每日凌晨 03:00
   ├── 全量扫描证据库
   └── 与已有信号去重

3. 推理过程副产品
   ├── 对抗推理过程中发现的风险/机会
   └── 由 Judge Agent 输出 → 自动创建 Signal

4. 用户手动触发
   └── POST /api/signals/detect
```

```typescript
interface SignalDetectionConfig {
  incrementalOnImport: boolean      // 新证据入库时增量扫描，默认 true
  scheduledFullScan: boolean        // 定时全量扫描，默认 true
  fullScanCron: string              // 全量扫描 cron，默认 '0 3 * * *'
```

### M10: 数据源管理 (Data Source Management) ⭐ 新增模块

**核心职责**：管理外部数据源的爬虫配置、同步调度和导入任务，为证据库提供持续的外部数据供给。系统不提供实时公网搜索，所有外部数据通过本模块定期爬取并存入证据库。

| 数据源分类 | 按类型分类管理数据源 | P1 |

| 质量监控 | 监控爬取成功率和数据质量 | P1 |
| 数据映射规则 | 配置爬取数据到证据字段的映射 | P1 |
