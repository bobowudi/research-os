# ResearchOS 产品架构 v3.1

> 多源证据驱动的 AI 调研决策系统 — 内外视角对抗推理

---

## 一、产品定位

**一句话**：帮助企业把内外部证据转化为可执行决策的 AI 系统

**核心价值**：
- 不是单纯"看数据"，而是"做决策"
- 不是"单视角分析"，而是"内外对抗推理"
- 不是"一次性报告"，而是"闭环学习"

---

## 二、核心创新：内外对抗推理

### 2.1 传统方案 vs 本方案

```
传统方案:
┌─────────────┐     ┌─────────────┐
│  内部数据   │ ──▶ │   AI 分析   │ ──▶ 决策
└─────────────┘     └─────────────┘
问题：只有一个视角，容易陷入"信息茧房"


本方案:
┌─────────────┐     ┌─────────────┐
│  内部证据   │ ──▶ │  正方 Agent │ ──┐
│ (问卷/访谈) │     │ (Advocate)  │   │
└─────────────┘     └─────────────┘   │
                                      ├──▶ ┌─────────────┐
┌─────────────┐     ┌─────────────┐   │    │  裁判 Agent │ ──▶ 决策卡
│  外部证据   │ ──▶ │  反方 Agent │ ──┘    │   (Judge)   │
│ (舆情/竞品) │     │  (Critic)   │        └─────────────┘
└─────────────┘     └─────────────┘
优势：内外视角对抗，发现盲区，决策更全面
```

### 2.2 三方 Agent 职责

| Agent | 数据源 | 职责 | 输出 |
|-------|--------|------|------|
| **正方 (Advocate)** | 内部证据库 | 构建支持论据，最大化内部数据价值 | 支持论点 + 置信度 |
| **反方 (Critic)** | 外部证据库 | 寻找反对论据、外部风险、竞品视角 | 反驳论点 + 风险提示 |
| **裁判 (Judge)** | 正反方输出 + 全部证据 | 综合评估，提炼洞察，识别冲突和盲区 | 洞察 + 决策卡 + 行动建议 |

### 2.3 证据来源说明

所有证据均存储在 ResearchOS 证据库中，不做实时公网搜索：

| 证据类别 | 来源方式 | 说明 |
|---------|---------|------|
| **内部证据** | 企业自有数据导入 | 问卷数据、深度访谈、内部报告、历史研究 |
| **外部证据** | 定期爬虫采集入库 | 社媒舆情、竞品监控、行业报告、新闻资讯 |

### 3.2 证据分类体系

```
Evidence (证据)
│
├── InternalEvidence (内部证据)
│   ├── survey: 问卷数据
│   ├── interview: 深度访谈
│   ├── internal_data: 企业内部数据（销售、运营等）
│   └── historical: 历史研究项目
│
└── ExternalEvidence (外部证据) ← 定期爬虫采集入库
    ├── social: 社媒舆情
    ├── competitor: 竞品监控
    ├── report: 行业报告
    └── news: 新闻资讯
```

### 3.3 证据立场模型

**核心设计**：立场是相对于议题的，不是证据本身的属性

```typescript
// 证据表 - 不存储立场
interface Evidence {
  id: string
  tenantId: string
  sourceCategory: 'internal' | 'external'
  sourceType: EvidenceSourceType
  content: string
  summary: string
  tags: string[]
  confidence: number
  // ... 无 stance 字段
}

// 议题-证据关联表 - 存储相对立场
interface IssueEvidence {
  issueId: string
  evidenceId: string
  stance: 'pro' | 'con' | 'neutral'      // 相对于议题的立场
  stanceSource: 'ai' | 'manual'          // 立场来源
  stanceConfidence: number               // 置信度 0-100
  stanceReason: string                   // 判断理由
  relevanceScore: number                 // 相关性分数
  relationType: 'auto' | 'manual'        // 关联方式
}
```

### 3.4 洞察层模型

**Insight（洞察）** 是从多条证据中提炼的结构化观点，是 Evidence 和 DecisionCard 之间的关键抽象层：

```
Evidence (原始数据, 几十条碎片)
    │
    │ AI 提炼 / 用户手动创建
    ▼
Insight (结构化洞察, 粒度适中, 可复用)
    │
    │ 正反方引用
    ▼
DecisionCard (决策建议, 宏观结论)
```

**Insight 的生成方式**：
- **AI 自动生成**：推理引擎在对抗推理过程中自动提炼
- **用户手动创建**：用户从证据中总结自己的洞察
- **从证据转化**：将单条高价值证据直接提升为洞察

### 3.5 证据自动关联机制

当新证据入库时（手动创建、批量导入、M10 爬虫采集），系统自动将证据与现有议题匹配：

```
新证据入库
    │
    ├─ Step 1: 生成 Embedding 向量
    │
    ├─ Step 2: 与 active 议题做语义相似度匹配
    │
    ├─ Step 3: 阈值判断
    │   ├─ relevanceScore ≥ 0.7 → 自动关联 (relationType='auto') + 自动立场分析
    │   ├─ 0.5 ≤ score < 0.7   → 推荐关联（通知用户确认）
    │   └─ score < 0.5         → 不关联
    │
    └─ Step 4: 通知议题 owner
```

> **设计原因**：外部证据通过 M10 定期爬虫采集，如果全靠手动关联到议题，用户体验极差。自动关联机制确保新数据能即时服务于正在分析的议题。

|------|-----------|-----------|
| **证据立场** | Evidence 全局 stance | IssueEvidence 相对 stance |
| **立场来源** | 入库时固定 | 关联时 AI 分析 + 手动修正 |
| **正方数据源** | 所有证据 | 内部证据 |
| **反方数据源** | 同样用所有证据 | 外部证据 |
| **外部数据** | 无系统化采集 | 定期爬虫采集入库 |
| **洞察层** | 有定义但未落地 | 作为推理中间层，用户可交互 |
| **Agent 职责** | 正反方看同一数据 | 正方看内部，反方看外部 |
| **数据源管理** | 无 | 爬虫配置、同步调度、导入管理 |
